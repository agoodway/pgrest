# PgRest 0.2: PostgREST / Supabase compatibility — design

Date: 2026-11-14 · Status: draft for approval · Target release: **0.2.0** (one release, breaking)

## Intent

PgRest should let a team serve the PostgREST HTTP API from a Phoenix app, so that existing Supabase clients
(`@supabase/postgrest-js` / `supabase-js`, and the Elixir `supabase_postgrest` client) work unchanged. A key use case is
**moving off Supabase to Elixir while keeping Postgres** — including teams that already rely on Postgres row-level
security (RLS). "Compatible" must be a measured property (CI compares us against real PostgREST), not a README claim,
and performance must be comparable to PostgREST on the same database.

## Goals

1. **Fix every safety bug and silent-wrong-result bug** in 00-GAP-ANALYSIS P0, plus the newly found one below.
2. **Replace PgRest's invented syntax with the real PostgREST grammar**, covering everything PostgREST v12–v14 supports
   that supabase-js can emit (and the CORE/COMMON items of 02 generally).
3. **Add the missing features** (RPC, aggregates, media types, Range/HEAD, max-affected, tx=rollback, PUT, profiles,
   optional RLS mode, etc.).
4. **Harden the tests**: a compatibility fixture schema, ported PostgREST + supabase-js scenarios against a real DB, a
   **differential harness that runs the same requests against a real PostgREST container**, real supabase-js e2e, and
   property tests for the parser.
5. **Performance parity**: one SQL statement per read like PostgREST; compare query plans, latency, and DB work against
   PostgREST on the same data; add tracing so plans/SQL are observable.

## Non-goals (0.2)

- PostgREST server-admin features: config files/env vars, CLI, admin server/metrics, LISTEN/NOTIFY schema reload, pool
  tuning, JWT cache internals, custom media-type handler domains, OpenAPI customization.
- Features PostgREST itself removed: limited update/delete via order+limit (removed v13), `Prefer: params=single-object`
  (v13), raw text/xml/octet-stream scalar outputs and `raw-media-types` (v12), legacy GUCs (v12).
- Database introspection as the source of truth. **Ecto schemas registered as resources remain the contract** (what is
  exposed, columns, types, relationships). We derive table names and FK names from them.
- Backward compatibility with 0.1 quirks (few users; bump to 0.2).
- Depending on Authzura (see Composability).

## Governing principle: drop-in parity

Anyone should be able to swap PostgREST/Supabase for PgRest (or back) without clients noticing: same URLs, headers,
status codes, bodies and error codes. Where PgRest has its own concepts (Ecto resources, `scope/2`, the authorization
hook), their observable behavior is mapped onto the PostgREST/Postgres mechanism they stand in for. Any deliberate
difference (e.g. `require_filters_for_mutations`) is opt-out, documented, and turned off in the differential runner.
The differential harness is the arbiter.

The bar is: **an app using supabase-js (or `supabase_postgrest`) just works.** Transport-level details are not part of
parity: `Server`, `Date`, header order/casing, `Content-Length` vs chunked, connection handling, timing. The
differential runner compares status, body, and an explicit allowlist of semantic headers (`Content-Range`,
`Content-Type`, `Preference-Applied`, `Location`, `Content-Location`, `Content-Profile`, `Allow`, `Range-Unit`).

## Anti-goals (would be failure even if "working")

- Any request that silently returns or mutates different rows than PostgREST would. Prefer a PostgREST-shaped error.
- An authorization hole: anything (embeds, upserts, RPC, aggregates, spreads) that reads/writes rows outside
  `scope/2` / the authorization hook.
- "Compatible" asserted only by our own expectations — CI must compare against real PostgREST.
- Per-embed or per-row query fan-out on reads.

## Constraints

- Elixir 1.19 / OTP 28, Ecto 3.14, Postgrex 0.22, Plug 1.20; Postgres 16 (local container `authzura-postgres-1` on
  5432 belongs to the sibling project — PgRest gets its **own** `docker-compose.yml`; pick non-conflicting ports).
- `mix quality` stays green (warnings-as-errors, format, sobelow, ex_dna, doctor, credo strict, dialyzer).
- Public extension points stay: `PgRest.Resource` callbacks (`scope/2`, `changeset/3`, `after_load/2`, `handle_param/4`),
  `PgRest.Authorization`, `:context_builder`, telemetry.
- Pinned comparison target: **PostgREST v14.x** Docker image (newest major supabase-js ships explicit fixtures for —
  `types.generated-with-options-postgrest14.ts`); an informational CI job also runs latest (16.x). *(My call; revisit.)*
- Embedding uses PostgREST naming (table name / FK constraint / column hints). Ecto association names remain accepted as
  an alias where unambiguous. *(My call.)*

## New finding (P0)

**Embedded relations bypass the target resource's `scope/2`.** `select.ex` preloads never call `scope/2`, so
`GET /orders?select=*,customer(*)` scopes orders but not customers → cross-tenant read via embed. 0.2 must apply the
target resource's scope (and authorization) at every embed level, in filters on embeds, `!inner`, spreads and aggregates.

## Approaches considered (read path)

- **A. Keep Ecto preloads, patch them** (windowed preload queries for per-parent limit). Smallest change, but spreads,
  aggregates, nested `!inner`, order-by-embedded and embeds-after-write stay awkward; plans can't be compared to
  PostgREST's. Rejected.
- **B. Single statement via the Ecto query DSL** (lateral joins + `fragment` json_agg). Stays in Ecto, but runtime
  composition of aliased lateral subqueries to arbitrary depth fights the DSL. Rejected as the primary builder.
- **C. Single statement via our own parameterized SQL builder, shaped like PostgREST's**, with Ecto schemas as metadata
  and **Ecto-built scoped base queries spliced in as subqueries**. **Chosen** (maintainer left the how to me): easiest to
  keep in lockstep with PostgREST SQL, plans compare directly, removes per-row Elixir work.

## Design

### Pipeline

`Plug` → **Request parser** (path, method, query string as an *ordered* list, headers incl. Prefer/Accept/Range/
Profiles) → **AST** (select tree, logic tree, order, range, mutation spec) → **Planner** (resolves the AST against the
**relationship graph** built from registered Ecto schemas; validates columns; detects ambiguity; applies authorization
and scopes) → **SQL compiler** (one statement; JSON built in Postgres) → **Executor** (one transaction per request when
needed: RLS GUCs, tx=rollback, mutation + representation, max-affected) → **Responder** (status, Content-Range,
Preference-Applied, Location, media type).

### Parser

- NimbleParsec grammar for: select (alias `a:col`, cast `::type`, JSON paths `->`/`->>`, `*`, embeds with alias,
  hints `!fk|!col`, `!inner|!left`, spread `...`, aggregates `count()`, `col.sum()`, `col.avg()::int`, empty embeds),
  filters (`[not.]op[(any|all)].value`, all 21 operators incl. fts with `(config)`), logic trees (`or=(…)`, `and=(…)`,
  `not.or=…`, nested, embedded `rel.or=`), order (`col.desc.nullslast`, JSON paths, `rel(col)`), quoting/escaping
  (`"…"`, `\"`, reserved `,.:()`), `in.(…)` with quotes, Prefer (comma/whitespace tolerant, repeatable headers).
- Query string is parsed from `conn.query_string` preserving order and duplicate keys.
- Errors → PGRST100 (400) with PostgREST-like `details`.
- Invented 0.1 syntax (`?not.col=`, `is.not_null`, `/:resource/:id` paths?) is **removed**. *(`/:id` routes: my call —
  remove; PostgREST has none. Confirm in review.)*

### Relationship graph & planner

- Built at registry start from resource Ecto schemas: table (with `@schema_prefix`), columns+types, PK, associations
  (`belongs_to`/`has_one`/`has_many`/`many_to_many` via `join_through` table), FK constraint names (default Ecto/PG
  naming `<table>_<col>_fkey`, overridable per association via resource option), cardinality (o2o when FK is unique or
  PK=FK, declared via option).
- Embed resolution order mirrors PostgREST: target name (table or alias) → candidate relationships → hint disambiguation →
  PGRST200 (none) / PGRST201 (HTTP 300, details list) if ambiguous.
- Custom query params: a resource declares the keys its `handle_param/4` handles (`custom_params: ["search"]`); every
  other unknown key is a 400. `handle_param/4` runs on the root resource's scoped base query on reads only, as in 0.1
  (the demo's `?search=` keeps working). *(My call.)*
- Every source (root, each embed, junction) is the target resource's **scoped Ecto base query**
  (`resource.scope(from(t in Schema), context)`), compiled with `Ecto.Adapters.SQL.to_sql/3`, parameters renumbered and
  spliced as a subquery. This is how `scope/2` (and therefore Authzura, which returns scoped Ecto queries) composes.
- Unknown columns anywhere → 400 (42703 shape). Empty filter set on bulk PATCH/DELETE allowed (PostgREST allows it) but a
  plug option `require_filters_for_mutations` (default **true**) mirrors Supabase, which enables
  `pg-safeupdate`: return exactly its error (SQLSTATE 21000, `DELETE requires a WHERE clause` / `UPDATE requires a
  WHERE clause`, HTTP 400). *Verify the exact Supabase response during Phase 1.* `false` matches plain PostgREST; document how to turn off. This deliberately differs from PostgREST, so the differential runner sets it
  to false.

### SQL compiler (reads)

- Mirror PostgREST's `QueryBuilder` shape: root `SELECT … FROM (scoped root) t LEFT JOIN LATERAL (SELECT
  json_agg(…)/row_to_json(…) FROM (scoped child) c WHERE c.fk = t.pk [filters] [ORDER] [LIMIT/OFFSET]) …`, giving
  per-parent limits naturally; `!inner` → filter on `IS NOT NULL` of the lateral result at any depth; spreads → flatten
  columns of to-one, arrays of to-many; aggregates → grouped lateral subqueries; order by to-one embedded columns.
- Count: `exact` via window/CTE in the same statement (`count(*) over ()` or a CTE like PostgREST); `planned` via EXPLAIN;
  `estimated` per PostgREST's threshold semantics.
- Response body assembled in Postgres (`coalesce(json_agg(_postgrest_t), '[]')`-style) and streamed as-is. The final JSON is selected as `::text`
  so Postgrex does not decode it into maps. `after_load/2`
  becomes **opt-in** via an explicit resource option (`after_load: true`; overriding the callback alone is not
  detectable reliably): when set, the compiler decodes and calls it per row (documented perf cost);
  otherwise the JSON passes through untouched. Its signature changes to a **string-keyed map → map** and it runs on
  every row of that resource, root or embedded. *(My call; migration guide.)*
- Ecto type semantics on reads: values come back in database form, as PostgREST would return them. Columns are emitted
  under the Ecto **field** name (`col AS field` handles `source:` renames). String-backed `Ecto.Enum` is unaffected;
  integer-backed enums, encrypted/custom types and embedded schemas return raw DB values unless the resource opts into
  `after_load`. Documented. *(My call.)*
- Type casting for filter values uses Postgres casts in SQL (`$1::<type>`) where Ecto casting can't express it (ranges,
  jsonb, arrays, regconfig).

### Writes

- POST single/bulk: changeset per row (default `changeset/3` casts **all schema fields** — fix to match docs), then a
  **single multi-row INSERT** (`insert_all` or compiled SQL) inside a transaction; `columns=`, `missing=default`,
  upsert (`resolution=merge|ignore-duplicates`, `on_conflict=`) for single and bulk, merge only sets payload columns,
  upsert target constrained by scope. 201 vs 200 semantics per PostgREST.
- PATCH with filters: call `changeset(struct(Schema), payload, Map.put(context, :operation, :update))` once; drop
  `validate_required` errors for fields absent from the payload; any other error → 400 with details. The `SET` list is every supplied payload
  key (value read with `get_field/2` after cast, so explicit null/false/0 survive) plus callback-generated `changes`
  (`put_change`, `updated_at`), then one scoped
  `UPDATE … RETURNING`. Context also carries `operation: :create` on inserts so changesets can branch.
  *(Per-row changesets can't run on a set update. My call; document in the migration guide.)*
- DELETE with filters; PUT single-row upsert (PGRST105/114 rules).
- `return=minimal|headers-only|representation`, `Location`, `Content-Range` on writes, representation with
  `select=` + embeds by feeding RETURNING into the read compiler as a CTE (`WITH pgrst_source AS (INSERT … RETURNING *)
  SELECT … FROM pgrst_source …`) — PostgREST's exact technique.
- `Prefer: max-affected=N` + `handling=strict` (PGRST124, rollback), `tx=rollback|commit`, single-object Accept on writes
  (406 PGRST116 + rollback).

### RPC

- New `PgRest.Function` registration (module or registry entries) declaring: name, schema, args (name/type, variadic),
  return kind (scalar, composite, setof table → maps to a resource for embeds), volatility (GET allowed only for
  stable/immutable). Introspection helper to register declarations from `pg_proc` for a whole schema (in scope; see Authorization).
- `/rpc/fn` GET/POST/HEAD, named args, single unnamed json/jsonb param, filters/select/order/limit/embeds on
  set-returning results, PGRST202 (404) / PGRST203 (300).

### Errors

- Body always `{code, message, details, hint}`; codes per `02-postgrest-docs.md` §11 table; SQLSTATE→HTTP map;
  central translator rescuing `Postgrex.Error`, `Ecto.ConstraintError`, changeset errors (→ 400/409 with details);
  no leaking of `inspect` output or Ecto query text.

### Responses / headers

- `Content-Range` always on reads (`0-9/*` without count), 206/416 rules, `Range`/`Range-Unit`, HEAD, OPTIONS (Allow),
  `Preference-Applied` echoes only applied prefs, 204 without content headers.
- Media types: json, `vnd.pgrst.object+json` (406 on ≠1), `vnd.pgrst.array+json;nulls=stripped`, `text/csv`,
  `vnd.pgrst.plan` (+json/text,
  `for=`, `options=analyze|verbose|settings|buffers|wal`, gated by a plug option, off by default), 406 PGRST107 otherwise.
- `Accept-Profile`/`Content-Profile`: schema selection among registered resources' prefixes; `Prefer: timezone`.

### Authorization, RLS, composability

- **Rule: PgRest-only concepts fail like their Postgres equivalents.** `scope/2` plays the role of an RLS policy and the
  hook's column allowlist plays the role of column privileges, so their denials return exactly what PostgREST returns
  for RLS / privilege failures (42501, 401 for the anonymous role, 403 otherwise). A client cannot tell which mechanism
  denied it.
- Existing: `scope/2` and `PgRest.Authorization` stay. The hook gains an optional callback that runs **after**
  `scope/2` on the already-scoped query, once **per resource touched** (root, embeds, junctions, RPC results), still
  receiving `conn`; it may narrow the query further and return a column allowlist. This is the "richer authorization
  hook" Authzura's later stage needs, built as a general PgRest improvement; PgRest never depends on Authzura and vice
  versa.
- **Plan-review amendments (2026-11-14):**
  - **`authorize/4` is fail-closed per resource.** It is called with `:read` for every resource a request touches (root, embeds,
    junctions, RPC result resources), not only the root.
  - **`scope/2` is a predicate contract** (where/join/distinct only); per-parent permission limits come from the hook.
  - **Upsert/PUT conflicts are checked against the existing row atomically** (`ON CONFLICT … DO UPDATE … WHERE <in scope>`),
    not only after the write.
  - **RPC results use `result_scope: :stored_rows | :none`.** `:stored_rows` (the default, STABLE/IMMUTABLE only) keeps a row only
    when it equals an in-scope stored row. VOLATILE functions returning a scoped resource must declare `:none`.
  - **`response.headers` / `response.status` GUCs are supported in 0.2** (PGRST111/112).
  - **A minimal `PgRest.Catalog` reads column defaults** for `missing=default` (metadata only).
  - **Composite FKs are declared explicitly** through `relationships:`.
  - Details: the three plans in `docs/superpowers/plans/`.
- Column allowlist semantics: `select=*` expands to the allowed columns (our extension; documented). Naming a hidden
  column anywhere (select, filter, order, aggregate, write payload) → 42501 `permission denied for table <t>`, as a
  Postgres column-privilege failure would.
- **Write check (scope as RLS `WITH CHECK`):** after INSERT/UPDATE/upsert, inside the same transaction, the written rows
  must still satisfy the resource's scope (and hook); otherwise roll back and return 42501
  `new row violates row-level security policy for table "<t>"` — the exact PostgREST response. An upsert that conflicts
  with a row outside scope gets the same response.
- **RPC authorization:** only registered functions exist; an unregistered one is PGRST202 (404), as PostgREST answers
  for a function not in its schema cache. The hook sees operation `:execute`; a denial is 42501
  `permission denied for function <f>`. Functions returning rows of a registered resource have that resource's scope
  applied to their results. To make switching painless, the introspection helper that registers every function in a
  schema (mirroring PostgREST exposing a whole schema) is **in scope for 0.2**.
- **Optional RLS mode** (`rls: [role_claim: "role", default_role: "anon", jwt: …]`): per request, in a transaction,
  `SET LOCAL ROLE <role>` and `set_config('request.jwt.claims', <json>, true)` (+ `request.headers`, `request.method`,
  `request.path` GUCs as PostgREST does), optional `pre_request` function. JWT verification via an injectable verifier
  (JOSE optional dep, or the host app verifies and passes claims via `:context_builder`). Off by default. Tests use the
  PostgREST fixture roles (`anon`, `authenticated`-like) and RLS policies, compared differentially against PostgREST with
  the same JWT secret.

### Telemetry & tracing

- Span per request with metadata: resource(s), operation, compiled SQL text + param count, row count, plan (when
  explain enabled), timings for parse/plan/compile/execute/encode. Fix README prefix (`[:pgrest, …]`).

## Testing & comparison infrastructure

- **Own `docker-compose.yml`**: Postgres 16, `pg_stat_statements` preloaded,
  PostgREST v14 (pinned) pointed at the same DB, both on non-default ports.
- **Compatibility fixture**: one SQL schema + seed (mirroring the relationship shapes in `03` "fixture shapes" and `05`
  fixture: m2o/o2m clients→projects→tasks, m2m users_tasks, composite-FK m2m, true o2o PK=FK, self-ref with two FKs,
  multiple FKs between the same tables, 3-level nesting, nullable FK, ranges/arrays/jsonb/tsvector columns, RPC
  functions, RLS policies, roles/grants) **plus matching Ecto resource modules** under `test/support/compat/`. Loaded into
  a dedicated database (not the Ecto sandbox — PostgREST can't see sandbox transactions).
- **Golden scenarios as data** (`test/compat/scenarios/*.exs` or JSON): request (method, path, headers, body) +
  expectations. Two runners:
  1. **Expectation runner** (always on): PgRest response vs recorded expectation.
  2. **Differential runner** (`mix test --only differential`, CI service containers): same request to PgRest and
     PostgREST; compare status, selected headers (Content-Range, Preference-Applied, Location, Content-Type), and body
     (JSON-normalized; order-insensitive only where scenario says). Mutations run with `Prefer: tx=rollback` on both or
     reseed between groups. A tool to **record** expectations from PostgREST seeds the expectation files.
  Port ~210 MUST-PORT scenarios from `03` and the MUST-PORT runtime scenarios from `05`; add explicit `order`.
- **Real supabase-js e2e**: small Node project in `test/js/` using `@supabase/postgrest-js` (pinned) against PgRest
  running on Bandit, executing the same calls as `05`. CI job; locally optional.
- **Property tests** (StreamData) for parser round-trip and escaping.
- Keep the existing Elixir `supabase_postgrest` integration tests, rewritten onto the compat fixture.

## Performance parity

- **Scenarios**: a benchmark set drawn from the golden scenarios (flat filter, deep embeds 3 levels, m2m, `!inner`,
  counts, aggregates, bulk insert 1k rows, upsert, RPC set-returning) on a scaled dataset (e.g. 100k–1M rows, generated).
- **Plans**: for each scenario capture PostgREST's plan (`Accept: application/vnd.pgrst.plan+json` with
  `db-plan-enabled`) and PgRest's (same media type, or EXPLAIN of the compiled SQL); compare node types, index usage,
  estimated/actual rows, buffers. Report diffs; flag seq scans where PostgREST uses indexes.
- **DB work**: `pg_stat_statements` deltas per scenario (calls, total time, shared blocks) — expect **1 statement per
  read** for PgRest (plus RLS GUC setup when enabled), same as PostgREST.
- **Latency/throughput**: HTTP load against both (tool of builder's choice from what's installed — oha/k6/wrk; never a
  browser), p50/p95/p99 and RPS at fixed concurrency; Benchee for in-process parse/plan/compile cost.
- **Target**: PgRest p95 ≤ 1.25× PostgREST and identical statement count per scenario; plan shape equivalent (same
  scan/join strategy) for all read scenarios. Results committed as a report under `bench/`
  (with the scripts that produce them).

## Phasing (all ships as 0.2.0)

No 0.1.x patch release: the maintainer chose to ship everything, safety fixes included, as 0.2.0. The P0 fixes land
directly in the new pipeline rather than being patched into 0.1 code that Phase 1 deletes.


1. **Phase 1 — Foundations, safety, grammar, single-statement reads.** docker-compose + compat fixture + expectation &
   differential runners + error shape first; then P0 fixes (unknown columns, duplicate keys, embed scope bypass,
   upsert scope, merge nil-fill, default changeset, FTS cast, 500s), new parser, relationship graph/planner, SQL compiler
   for reads, embeds (hints, inner/left, spreads, per-parent limits, order by embed, embedded filters with all ops),
   Content-Range/Range/HEAD, writes with representation+embeds. Port the matching MUST-PORT scenarios as each lands.
2. **Phase 2 — Missing features.** RPC, aggregates, media types (csv, nulls=stripped, plan), max-affected,
   tx=rollback, PUT, profiles, timezone, OPTIONS, optional RLS mode (+ RLS differential tests), richer authorization
   hook, supabase-js e2e harness. Remaining MUST/SHOULD scenarios.
3. **Phase 3 — Performance parity & tracing.** Scaled dataset, plan comparison tooling, pg_stat_statements capture, load
   tests, Benchee, telemetry enrichment, fix plan/perf gaps found, publish report. CI keeps differential on every PR;
   perf runs on demand / nightly.

Release: README/CHANGELOG/migration guide from 0.1 (removed syntax, error shape, `/:id` routes, changeset default),
version bump to 0.2.0.

## Future (not in 0.2) — notes

- **Syntax/extension adapters**: a pluggable layer so apps can add custom operators/syntax and extension-aware types
  (e.g. PostGIS operators and functions, and GeoJSON output via `application/geo+json`). Keep the parser
  operator table and compiler operator → SQL mapping data-driven so this is additive later.
- Introspection-based resource generation, OpenAPI at root, computed relationships, schema-cache reload.
