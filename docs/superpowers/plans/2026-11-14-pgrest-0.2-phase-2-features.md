# PgRest 0.2 — Phase 2: Missing Features — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add the PostgREST features Phase 1 left out: RPC (including the `response.headers`/`response.status` GUCs), aggregates, media types, strict preferences, PUT, OPTIONS, multi-schema profiles, timezone, optional RLS mode and the richer authorization hook. Prove them with recorded and differential PostgREST scenarios, including RLS with real roles, and with a real `@supabase/postgrest-js` e2e suite.

**Architecture:** Phase 2 extends the Phase 1 pipeline (`PgRest.Request` → grammar → `PgRest.Planner` → `PgRest.SQL.*` → `PgRest.Executor` → `PgRest.Responder`). It does not replace it.
- **Registry:** `PgRest.Registry` becomes a named, schema-aware snapshot published to `:persistent_term`. It holds resources, the relationship graph and registered `PgRest.Function`s.
- **RPC:** an RPC call is a read plan whose source is a function call instead of a scoped table. Filters, select, order, embeds, count, media types and scope therefore apply unchanged.
- **Transactions:** a per-request transaction "setup" is **one** `SELECT set_config(...)` statement (read-only flag via `transaction_read_only`, `statement_timeout`, timezone and the RLS GUCs), followed by the optional `pre_request` call. There is no separate `SET TRANSACTION`.
- **Authorization:** Phase 1 Task 10 already calls `authorize/4` fail-closed for every resource a request touches, and Phase 1 makes writes with filters/representation/count/`Location` also need `:read`. Phase 2 extends that loop to functions (`:execute`), RPC result resources (`:read`) and plan output (`:explain`). The new optional `authorize_query/5` hook runs per plan node, after `scope/2` and after `authorize/4` has allowed that resource. It can only narrow: it returns a narrowed, predicate-only Ecto query, a column allowlist, an optional per-parent row `limit:`, and `aggregates:`/`count:` permissions. When an `:authorization` module is configured, **a callback it does not export denies** (Task 14).
- **RPC exposure:** introspected functions are never exposed wholesale in default (non-RLS) mode. Introspection needs an explicit `only:`/`except:` list or an `:authorization` module exporting `authorize/4`, filters by `has_function_privilege`, and always skips extension-owned and trigger/internal functions (Task 4).
- **Response GUCs:** every read, write and call statement also returns `response.headers` and `response.status`, which the Responder applies (Task 6b).

**Tech Stack:** Elixir 1.19 / OTP 28, Ecto 3.14, Postgrex 0.22, Plug 1.20 (incl. `Plug.Crypto`), NimbleParsec, StreamData, Req, Bandit (test), Docker Compose (Postgres 16, a pg-safeupdate Postgres, PostgREST v14 ×2: `test`, `supabase`), Node 22 LTS + pinned `@supabase/postgrest-js` (test only).

## Global Constraints

- **Drop-in parity governs:** a supabase-js app must just work.
  - Transport details (`Server`, `Date`, header order and casing, chunking) are not compared.
  - The semantic headers that are compared: `Content-Range`, `Content-Type`, `Preference-Applied`, `Location`, `Content-Location`, `Content-Profile`, `Allow`, `Range-Unit`.
- Comparison target: the exact `postgrest/postgrest:v14.<patch>` tag pinned in Phase 1 Task 1. Every new PostgREST service in this plan uses that same tag.
- PgRest-only concepts fail like their Postgres equivalents: scope behaves like RLS (42501), the hook's column allowlist like column privileges (42501), and an unregistered function like an uncached one (PGRST202). **The recorded PostgREST response is authoritative** for status, code, message, details and hint. Where this plan quotes a message from the reference source, a recording that differs wins.
- Ecto schemas registered as resources are the contract for tables. Phase 2 adds `pg_proc` introspection **for functions only** (spec "RPC"); tables are still never introspected.
- One SQL statement per read. Exceptions:
  - One `SELECT set_config(...)` setup statement, when RLS mode, `Prefer: timezone`, `statement_timeout` or a read-only RPC needs a transaction. Read-only is `set_config('transaction_read_only', 'on', true)` and `statement_timeout` is `set_config('statement_timeout', $n, true)`, both folded into that one statement. Never a separate `SET TRANSACTION` (P-M2).
  - The `pre_request` call.
  - Phase 1's write-check statement.
- **Repo calls** follow Phase 1: every PgRest statement, including the Phase 2 setup statement, `pre_request`, introspection, `Catalog.facts/1` and `EXPLAIN`, passes `log: false` and `telemetry_options: [pgrest: true]`. The setup statement binds `Authorization`-bearing headers, cookies and claims, so it must never reach Ecto's log or query telemetry (S-M3).
- **Phase 1 plug options are consumed, not redefined** (Phase 1 Task 11 owns the list): `max_limit` (root and every embed lateral, RPC embeds included), `max_embed_depth` (8), `max_body_bytes` (8_000_000 → 413, RPC POST bodies included), `max_bulk_rows`, `count_modes`, `tx_end` (default `:commit`; `Prefer: tx=rollback` is honoured only under `:commit_allow_override`), `statement_cache` and `statement_timeout`. **Every compat router in this plan sets `tx_end: :commit_allow_override`**, as the PostgREST services run with `PGRST_DB_TX_END=commit-allow-override`.
- **Casts.** A cast type name that comes from the request (select/aggregate `::cast`, aggregate `input_cast`) is accepted only by the grammar's `^[A-Za-z_][A-Za-z0-9_ $]*(\[\])?$` rule (63-byte maximum) and emitted only through Phase 1's `PgRest.SQL.Builder.cast/2` as `CAST(<expr> AS <type>)` (S-H2). Type text from the catalog (`PgRest.Catalog.column_types/3`, `pg_proc`'s `format_type`) is never request-derived and is emitted the way Phase 1 emits `column_types/3` text. Filter casts on table columns use `column_types/3`; filter casts on non-resource RPC composites use `Return.columns` types (P-H3).
- **Error details are scrubbed** like Postgres does under RLS: every `Error.Translate.from_exception/3` call passes `scrub_details?: true` when the request's effective source (`Plan.Read.source_query`) is not the identity, when a hook narrows, or when any column allowlist (hook `columns:` or resource `readable:`/`writable:`) is not `:all`. Then `details` is `nil` for 23502, 23503, 23505, 23514 and 23P01 (S-H5).
- **Guards use correlated `EXISTS`**, never `IN (subquery)`: the PUT conflict guard, the write check and the `:stored_rows` RPC wrap all probe `(<ScopedSource>)` by key (P-H4). `Plan.Read.source_query` is defined by Phase 1; Phase 2 fills it with the hook-narrowed query and never defines it again (P-M3).
- **Compose services are a test harness only.** Every Phase 2 service binds `127.0.0.1:<port>:<container port>`, has no `restart:` policy, and sits under the compose file's "test harness only" header (Phase 1). User-facing docs never show a superuser anon role, the `authenticator` password or the shared JWT secret (S-M5).
- **Supply chain:** `npm ci --ignore-scripts`, and every GitHub Action Phase 2 adds (`actions/setup-node`) is pinned by commit SHA (S-L6).
- `require_filters_for_mutations` plug option defaults to `true` (Supabase `pg-safeupdate` parity: SQLSTATE `21000`, message `DELETE requires a WHERE clause` / `UPDATE requires a WHERE clause`, HTTP 400). Differential runner sets it `false` except in the `safeupdate` area (Task 2).
- New plug options and their defaults, mirroring PostgREST's:
  - `registry: PgRest.Registry`
  - `aggregates: false`, mirroring `db-aggregates-enabled`
  - `plan_enabled: false`, mirroring `db-plan-enabled`. It accepts `false | true | (Plug.Conn.t(), context -> boolean())`; when an `:authorization` module is configured the plan media type is also gated by its `:explain` operation (Task 9, S-M4).
  - `rls: nil`. When set, `roles:` (an allowlist) is required and `allow_privileged_login:` defaults to `false` (Task 13, S-H3).
  - `anonymous?: &PgRest.Auth.default_anonymous?/2`

  Compat routers set `aggregates: true`, `plan_enabled: true` and `tx_end: :commit_allow_override` (the PostgREST services run with all three).
- **Authorization fails closed on missing callbacks** (S-M1). When `:authorization` is configured: no `authorize/4` export means `:execute` and `:explain` are denied and table operations fall through to `authorize_query/5`; no `authorize_query/5` export means every operation, writes included, still needs `authorize/4`; a module exporting neither denies everything. The hook must return `{:error, _}` for operations it does not implement.
- **No new runtime dependencies.** JWT HS256 is verified with `:crypto` + `Plug.Crypto.secure_compare/2`. Node is test-only, under `test/js/`.
- Breaking changes are fine (0.2). `mix quality` must pass at the end of every task (compile --warnings-as-errors, format, sobelow, ex_dna, doctor, credo --strict, dialyzer).
- **Git:** never run `git commit`, `git push`, `git tag`, `git add` or anything that changes the index or HEAD, and never `mix hex.publish`. The maintainer stages and commits. A "Suggest a commit message" step means: leave the work in the working tree and propose a message (no AI attribution); the maintainer decides if and when to commit.

Also load `elixir-phoenix-guide:ecto-essentials` for Ecto/SQL work, `elixir-phoenix-guide:testing-essentials` for tests, `elixir-phoenix-guide:otp-essentials` for the Registry (Task 3), and `elixir-phoenix-guide:security-essentials` for JWT/RLS/hook (Tasks 13–14).

  - `Req` for HTTP and `Jason` for JSON.
- **Never create atoms from request input.** That includes function names, argument names, schema/profile names, role names, JWT claim keys, media-type parameters and `Prefer` values. Resolve them by string lookup in the registry snapshot. Unknown names become PostgREST errors, not `ArgumentError`. SQL identifiers that come from config or the registry are always quoted with `PgRest.SQL.Builder.ident/1`. Values (roles, GUC values, timezone) are always bind parameters.
- Version stays `0.1.0` until the Phase 3 release task.

- **Bind parameters follow Phase 1** (Global Constraints, `PgRest.SQL.Builder.param` with `mode: :text | :native`). Request-derived values, RPC arguments included, are bound as text and cast in SQL, `$n::text::<pgtype>`, never `$n::<pgtype>`. JSON payloads are bound once as `$n::text::json`/`$n::text::jsonb`. Only values produced in Elixir (`Ecto.Type.dump/2`, GUC names and values built by PgRest) are bound `:native`.
- **`scope/2` is a predicate contract** (Phase 1 Global Constraints): `where`, `join` and `distinct` only. The `authorize_query/5` hook's query follows the same contract (Task 14). Per-parent permission limits come only through the hook's explicit `limit:`.
- **Authorization is fail-closed per resource** (Phase 1 Global Constraints and Task 10). Nothing in Phase 2 narrows that loop. Phase 2 adds `:execute` on functions, `:read` on RPC result resources and `:explain` on plan output.
- **Writes need `:read`** (Phase 1 rule, S-H1). PATCH, DELETE, PUT and upsert with filters, `return=representation`, count or `Location`, and INSERT with `return=representation`, are authorized with `:read` as well as the write operation. Phase 2 extends this to `authorize_query/5`: the `:read` result supplies the row narrowing and the column set for filters, order, `RETURNING`, representation and counts; the write-operation result supplies the payload column set and the check predicate (Task 14). PUT always has PK filters, so PUT always needs `:read`.
- **Introspection is never schema-wide by default** (S-C1, Task 4). In non-RLS mode `introspect:` requires `only:`/`except:` or an `:authorization` module exporting `authorize/4`, or registry start raises. `as_role:` keeps only functions the role may `EXECUTE`. Extension-owned functions and functions returning `trigger`, `event_trigger` or `internal` are always skipped.
- **Registry startup never calls `scope/2`.** Every startup requirement is static: declared options (`result_scope:`, `unique_key:`), the resource's compile-time config and the schema. Whether a scope is the identity is decided per request, with the real context (`ScopedSource.identity_scope?/2`).
- Shared JWT secret (PostgREST's own spec secret, ≥32 chars): `reallyreallyreallyreallyverysafe`.
- Scenario conventions are exactly Phase 1's.
  - Each task adds scenarios, records them with `mix pgrest.compat.record <area>`, lists their ids in `test/compat/pending.txt` until green, and removes them when green.
  - Every backlog entry a task ports is ticked in `test/compat/phase2_backlog.md` with the scenario id (`- [x] … → rpc/getallprojects-filters`).
  - Mutating scenarios send `Prefer: tx=rollback` and set `stateful: true`. They run serially in the stateful module, under the Phase 1 sequence protocol: `Fixture.reset_sequences!/1`, PgRest, `reset_sequences!/1`, PostgREST. This applies to every fixture database (Task 1 captures a baseline per database).
  - Bodies are compared by `Compare.diff`'s content-type mode (Phase 1 Task 3). CSV, `text/plain` and plan text are compared as raw text, and an empty or 204 body equals only another empty body.
  - Every fixture database Phase 2 adds follows the Phase 1 reload-marker protocol (Task 1).

## Review Focus

1. **Column-allowlist bypass through indirect references.** A hidden column must give 42501 when it appears as a JSON path (`secret->>k`), a cast (`secret::text`), an aggregate input (`secret.sum()`), inside `or=(secret.eq.1)`, as an embedded filter or order (`rel.secret=eq.1`, `rel.order=secret`), in `on_conflict=secret`, in `columns=secret`, or as a write payload key. Test owned by Task 14.
2. **Role/GUC leakage across pooled connections in RLS mode.** After a request that errors mid-transaction (42501, `pre_request` raise, `statement_timeout`), the next request on the same single connection must run as the default role with fresh claims. `SET LOCAL` / `set_config(..., true)` only; never session-level `SET`. Test owned by Task 13.
3. **Aggregates and RPC as scope bypasses (anti-goal).**
   - `count()`/`sum()` over a scoped resource and aggregates inside an embedded scoped resource must see only in-scope rows.
   - A STABLE/IMMUTABLE function returning rows of a scoped resource (`result_scope: :stored_rows`) must return only rows that match an in-scope stored row on the PK **and** on every mapped column. A fabricated composite (no stored row) and a real PK whose ownership attribute was rewritten by the function must both be dropped.
   - A VOLATILE function returning a scoped resource without `result_scope: :none` must fail registration.
   - An `authorize/4` that denies the result resource must deny the RPC, even when `:execute` is allowed.
   - Tests owned by Tasks 4 and 6 (RPC) and Task 7 (aggregates).
4. **RPC argument ambiguity and binding.** On GET, a parameter whose value parses as a filter (`?name=eq.x`) is a filter, not an argument. Extra JSON keys give PGRST202, not "ignored". Repeated non-variadic GET keys: last wins. A bigint sent as a JSON string, an explicit `null` argument, and an omitted defaulted argument must all behave like PostgREST. Every argument is bound as text (`$n::text::<type>`) and really executed. A malformed argument (`add_them?a=abc&b=2`) returns the recorded `22P02` response, not a Postgrex encode error. Test owned by Task 6.
5. **CSV escaping.** Committed fixture rows containing `,`, `"`, newlines, unicode, NULL, the empty string, jsonb and arrays, plus an empty result set (whatever header/body PostgREST emits for zero rows), must be byte-identical to PostgREST's `asCsvF` output under `Compare.diff`'s raw-text mode. Test owned by Task 8.
6. **Response GUC handling.** `response.headers` must be a JSON array of single-key objects with string values, or the response is PGRST111. `response.status` must be a valid status code, or the response is PGRST112. A GUC header replaces a PgRest-generated header of the same name (case-insensitive). Repeated GUC headers (two `Set-Cookie`) are all sent. GUCs set by a failing statement are never applied. Test owned by Task 6b.
7. **Per-parent hook limits.** A hook `limit: n` on an embedded resource caps rows **per parent**, inside each lateral, never globally. A hook query carrying `limit`/`offset`/`order_by`/`group_by` raises instead of being spliced. Test owned by Task 14.
8. **RPC exposure in default mode (S-C1).** `introspect: [repo: Repo]` with no `only:`/`except:` and no `authorize/4` module must refuse to start. Under `:supabase_scope`, anon `POST /rpc/privileged_hello` must be 401 exactly like PostgREST. Extension functions (`pg_trgm`'s `similarity`) and trigger functions must never be callable. Tests owned by Task 4 and Task 14.
9. **Write as a read channel (S-H1).** A role allowed `:update` but denied `:read` (or allowed only some readable columns) must get 42501 from `PATCH ...?value=like.a*` with `return=representation`, with `count=exact`, or with a bare filter, and a writable-but-not-readable column must never be returned or filterable. Test owned by Task 14.
10. **Hook fail-closed (S-M1).** A deny-by-default module exporting only `authorize_query/5` must deny every `:execute`, every `:explain`, every write it returns `{:error, _}` for, and aggregates/counts unless it returns `aggregates: true`/`count: true`. Tests owned by Tasks 6, 9 and 14.
11. **RLS role claim (S-H3).** A token whose role claim is `none`, `session_user`, `postgres` or anything outside `rls[:roles]` gets 401 before any SQL runs; a superuser or `BYPASSRLS` login role refuses to serve without `allow_privileged_login: true`. Test owned by Task 13.
12. **Constraint details in scope mode (S-H5).** A check or unique violation under a non-identity scope or allowlist returns `details: null`, byte-identical to PostgREST under RLS. Test owned by Task 14.

  - `%PgRest.Function.Param{name: String.t(), type: String.t(), required?: boolean(), variadic?: boolean()}`
    - Only IN, INOUT and VARIADIC params appear here.
    - `name` is `""` for an unnamed param.

    - `columns` comes from the composite type's attributes, or from OUT/INOUT/TABLE params.
    - A function with any OUT/TABLE params is `:composite`, including a single OUT param (RPC:779).
    - `record` without OUT params is `:composite` with `columns: []`, which means no select or filter is allowed.
    - `resource` is set when the composite type is `{schema, table}` of a registered resource.

    - Param tuples are `{name, type}` or `{name, type, default: true}` / `{name, type, variadic: true}`.
    - `returns` is one of `:void | {:scalar, type} | {:setof_scalar, type} | {:composite, resource_module | [{col, type}]} | {:setof, resource_module | [{col, type}]}`.
    - Overloads are separate modules.
  - `PgRest.Function.Introspect.load(repo, schemas :: [String.t()], resource_configs :: [map()]) :: {:ok, [PgRest.Function.t()]} | {:error, Exception.t()}`.
    - One query over `pg_proc p JOIN pg_namespace n`, filtered by `p.prokind = 'f' AND n.nspname = ANY($1)`.
    - It reads `proname, provolatile, proretset, prorettype, pronargdefaults, proargnames, proargmodes, coalesce(proallargtypes, proargtypes::oid[])`.
    - Return type: `typtype` and `typrelid`. Composite columns come from `pg_attribute` (`attnum > 0 AND NOT attisdropped`, ordered by attnum). Use `array_agg`/`json_agg` subselects so it stays one statement.
    - The last `pronargdefaults` input params are `required?: false`.
    - **Always skipped** (S-C1): extension-owned functions (`NOT EXISTS (SELECT 1 FROM pg_depend d WHERE d.classid = 'pg_proc'::regclass AND d.objid = p.oid AND d.deptype = 'e')`) and functions whose return type is `trigger`, `event_trigger` or `internal`.
    - With `as_role`, a function is kept only when `has_function_privilege(r, p.oid, 'EXECUTE')` holds for at least one listed role; role names are bind parameters.
    - `only:` keeps exactly the listed names and `except:` drops them, matched as strings.
    - Otherwise computed-field-shaped functions remain callable/unreachable exactly as PostgREST resolves them (05 §9 `blurb_message`).
    - Full signature: `Introspect.load(repo, schemas, resource_configs, filter :: %{only: [String.t()] | nil, except: [String.t()], as_role: [String.t()] | nil})`.
  - Registry options:
    - `functions: [module()]` (module-declared).

**Interfaces:**
- Consumes: `Snapshot.functions/3`, `PgRest.Grammar.Filter.parse_condition/2`, `PgRest.Request`.
- Produces:
  - `PgRest.RPC.Args.split(Request.t(), invocation :: :read | :post) :: {arg_keys :: [String.t()], filter_params :: [{String.t(), String.t()}]}`. The reserved keys `select`, `columns`, `on_conflict`, and any key ending in `order`/`limit`/`offset`/`and`/`or`, always go to `filter_params`.
    - `:read` (GET/HEAD), for each remaining key: if `Filter.parse_condition(key, value)` succeeds it is a filter. Otherwise it is an argument (PostgREST `pRequestFilter isRpcRead`).
    - `:post`: `arg_keys` are the keys of the JSON object body, in body order and deduplicated. `[]` for an empty body. All query params are filters.
  - `PgRest.RPC.Resolver.resolve(snap, schema, name, arg_keys, invocation) :: {:ok, PgRest.Function.t()} | {:error, PgRest.Error.t()}`. This is a port of `Plan.hs` `findProc` over `Snapshot.functions/3`.
    - A function **matches** when one of these holds:
      - It has no params and `arg_keys == []`.
      - It has only required params and the key set equals the required names.
      - It has only optional params and the keys are a subset of them.
      - It has both, and the keys minus the optional names equal the required names.
    - A **fallback** is a POST to a function with exactly one unnamed `json`/`jsonb` param.
    - Outcome:
      - One match: that function.
      - No match and one fallback: the fallback.
      - Several matches, or no match and several fallbacks: 300 PGRST203.
      - Nothing at all: 404 PGRST202.
  - Error texts, exact per `Error.hs`:
    - PGRST203 message: `Could not choose the best candidate function between: <s>.<f>(<p> => <type>, …), …`. Hint: `Try renaming the parameters or the function itself in the database so function overloading can be resolved`. Details: null.
    - PGRST202 message: `Could not find the function <s>.<f>(<k1>, <k2>) in the schema cache`, or `… <s>.<f> without parameters in the schema cache` when there are no keys. Keys keep request order.
    - PGRST202 details: `Searched for the function <s>.<f> with parameter <k>` (or `with parameters <k1>, <k2>`, or ` without parameters`). On POST it appends ` or with a single unnamed json/jsonb parameter`. It always ends with `, but no matches were found in the schema cache.`
    - PGRST202 hint:
      - When no function has that name: `Perhaps you meant to call the function <s>.<closest name>`, using `Suggest.closest(name, names_in_schema, 0.75)`.
      - Otherwise: `Perhaps you meant to call the function <s>.<f>(<closest param list>)`, using `Suggest.closest(Enum.join(keys, ", "), param_lists_of_overloads, 0.33)`.
      - `nil` when there is no suggestion.
  - `PgRest.Error.Suggest.closest(term :: String.t(), candidates :: [String.t()], min_score :: float()) :: String.t() | nil`. This ports Haskell `Data.FuzzySet` defaults (`gramSizeLower 2`, `gramSizeUpper 3`, `useLevenshtein True`):
    1. Normalize each string by downcasing it and replacing every character that isn't a letter, digit, `,` or space with nothing. Pad it as `"-" <> s <> "-"`.
    2. For gram size 3, then 2: compute the cosine similarity of the n-gram count vectors against every candidate.
    3. Keep the top 50, rescore each as `1 - levenshtein(term, cand) / max(len)`, and keep those ≥ `min_score`.
    4. The first gram size that yields any candidate wins; return its highest score.

    If Phase 1 already computed the PGRST205 "Perhaps you meant the table" hint some other way, switch it to this module (`min_score 0.75`).

- Produces:
  - In `PgRest.Authorization`, a new optional callback (built generically for external deny-by-default policy libraries; PgRest depends on none):

```elixir
@callback authorize_query(
            conn :: Plug.Conn.t(),
            resource :: module(),
            operation :: :read | :create | :update | :delete | :explain,
            query :: Ecto.Query.t(),
            context :: map()
          ) ::
            {:ok, Ecto.Query.t()}
            | {:ok, Ecto.Query.t(),
               opts :: [
                 columns: :all | [String.t()],
                 limit: pos_integer() | nil,
                 aggregates: boolean(),
                 count: boolean()
               ]}
            | {:error, term()}
@optional_callbacks authorize_query: 5
```

  - **Hook opts** `aggregates:` and `count:` (S-M1, the `allow_aggregations` counterpart of Hasura-style policy engines) both default to `false` when `authorize_query/5` is exported: a hook that does not say so denies aggregates (`count()`, `sum()`, legacy bare `count`) and `Prefer: count=exact|planned|estimated` on that resource. A denial is `permission_denied(:table, table, req)`. A 2-tuple `{:ok, q}` means `columns: :all, limit: nil, aggregates: false, count: false` (my call: fail-closed, matching the deny-by-default engines this hook targets). Modules exporting only `authorize/4` keep Phase 1 behaviour.
  - The hook must return `{:error, _}` for any operation it does not implement; `:explain` is asked by Task 9.

  - **`authorize/4` keeps Phase 1 Task 10's fail-closed, per-resource contract.** The hook builds on top of it and never replaces it:
    - `authorize/4` runs with `:read` for every resource touched: root, every embed, m2m junctions, RPC result resources and write-representation embeds. It runs with the write operation on a write target and with `:execute` on functions (Task 6).
    - For each resource, `authorize/4` runs first. Only if it allows does `authorize_query/5` run for that resource, and the hook can only narrow further.
    - **Missing callbacks deny** (S-M1, Global Constraints). A module may export either callback or both, but: with no `authorize/4`, `:execute` and `:explain` are denied and table operations are decided by `authorize_query/5` alone; with no `authorize_query/5`, every operation, writes included, is decided by `authorize/4`; a configured module exporting neither denies everything.
    - A denial from either is `permission_denied(:table, table, req)` (401/403 by `authenticated?`).
  - **Writes need `:read` in the hook too** (S-H1, extending Phase 1's `authorize/4` rule). For PATCH, DELETE, PUT and upsert with filters, `return=representation`, count or `Location`, and for INSERT with `return=representation`, the target gets two `Apply.source/6` calls:
    - `:read` supplies the row narrowing and the column set checked against filters, logic trees, order, `RETURNING`/representation, `select=` and counts;
    - the write operation supplies the payload column set (payload keys, `columns=`, `on_conflict=`) and the write-check predicate.

    A column that is writable but not readable can therefore be written but never returned, filtered or ordered.
  - **Resource allowlists** (Phase 1 `readable:`/`writable:`, `__schema__(:redact_fields)`) are intersected with the hook's `columns:`: the effective read set is `readable ∩ hook(:read).columns` and the effective payload set is `writable ∩ hook(<write op>).columns`. Both use the same 42501 path.
  - `PgRest.SQL.ScopedSource` splits in two; `build/4` stays and composes them:
    - `base_query(resource, context, custom_params) :: Ecto.Query.t()` is `scope/2` + `handle_param/4`.
    - `compile(Ecto.Query.t(), resource, Builder.t()) :: {iodata, Builder.t()}`. The hook's query is held to **the same predicate contract as `scope/2`** (Phase 1 Global Constraints): `where`, `join` and `distinct` are kept, and a join is spliced as the Phase 1 PK semijoin.
      - `select` and `preload` are stripped with `Ecto.Query.exclude/2` before `to_sql` (my call: column restriction is the allowlist's job, so a hook that "owns the select" can't drop columns the compiler needs).
      - `limit`, `offset`, `order_by` and `group_by` in a hook query raise `ArgumentError` naming the hook module and resource. A permission row limit must use the explicit `limit:` option.
  - **Per-parent permission limit** (`limit:` in the hook's opts; the select-permission `limit` of Hasura-style policy engines). It is compiled **inside each lateral**, per parent, never as a global limit on the scoped source:
    - Embedded node: the lateral's `LIMIT` becomes `LEAST(<request limit or ALL>, <hook limit>)`, after the parent correlation and the request filters. A hook limit of 1 on `tasks` gives every user at most one task, not one task overall.
    - Root node: the same `LEAST` with the request's `limit`. `Prefer: count=exact` counts over the capped root set, so `Content-Range` can't reveal more rows than are visible (my call).
    - Nodes with aggregates: the capped rows are selected in an inner subquery inside the lateral and aggregated outside it.
    - RPC result resources under `result_scope: :stored_rows` take the cap on the call's rows. Under `:none` the hook is not applied (Task 6).
  - `PgRest.Authorization.Apply.source(conn, authorization :: module() | nil, resource, operation, base :: Ecto.Query.t(), context) :: {:ok, %{query: Ecto.Query.t(), columns: :all | MapSet.t(String.t()), limit: pos_integer() | nil, aggregates?: boolean(), count?: boolean()}} | {:error, :denied}`.
    - It calls `authorize/4` first when exported (the Phase 1 loop, not a second call), then `authorize_query/5` when exported, applying the missing-callback rules above.
    - With no `:authorization` module, it returns `{:ok, %{query: base, columns: :all, limit: nil, aggregates?: true, count?: true}}`. With a module exporting only `authorize/4`, the same after `authorize/4` allows.
    - It runs **once per resource and operation per request** (P-M3); the result is stored in the plan and never recomputed. Its query goes through Phase 1's compiled-scoped-SQL cache keyed by `{resource, :erlang.phash2(query_without_params)}`.
    - The columns are **physical column names** (my call: matches Postgres column privileges and physical-name policy allowlists).
    - A `{:ok, q}` 2-tuple means `columns: :all, limit: nil`.
  - `PgRest.Authorization.Apply.check_columns(columns, resource, field_names :: [String.t()]) :: :ok | {:error, :denied}` maps field names through `field_sources`. `:all` always passes.
  - `Plan.Read.source_query` is **Phase 1's field** (the effective source, computed once per resource per request). Task 14 fills it with the hook-narrowed query instead of the bare scoped query and does not define it again. `Plan.Read` gains, per node (root and every embed's plan): `allowed_columns: :all | MapSet.t(String.t())`, `hook_limit: pos_integer() | nil`, `aggregates_allowed?: boolean()` and `count_allowed?: boolean()`. The write plans gain `payload_columns: :all | MapSet.t(String.t())`. The planner calls `Apply.source/6` once per resource and operation touched:
    - root read: `:read`;
    - root write: `:read` (when the S-H1 rule above applies) **and** the write operation;
    - embeds, m2m junctions that are registered resources, RPC `returns.resource`, and write-representation embeds: `:read`;
    - the write check: `:create` or `:update` (the write-operation result already computed, not a third call).

    The compiler uses `source_query` instead of rebuilding it. A narrowing hook counts as "not the identity" for Task 6 result scoping, for the Task 11/Phase 1 Task 13 conflict guard and for `scrub_details?` (Global Constraints, S-H5): `Error.Translate.from_exception/3` gets `scrub_details?: true` whenever any node's `source_query` is not the identity or any `allowed_columns`/`payload_columns` is not `:all`.
  - The column checks fail with `permission_denied(:table, <table>, req)` (401/403). A hidden column is denied when it appears in any of: a select field (including JSON path and cast), filter, logic tree, embedded filter, order and embedded order, aggregate input, group term, write payload key, `columns=`, `on_conflict=`, or PUT URL filter.
    - `select=*` (and `rel(*)`, `...rel(*)`, and the default representation after writes) expands to the allowed columns only (our documented extension).
    - Relationship join columns are not checked (my call: relationships are part of the contract; Hasura-style semantics).
    - Hook `{:error, _}` → `permission_denied(:table, …)`.
  - Test-support `PgRest.Compat.TenantAuthorization` is a deny-by-default policy module that **exports only `authorize_query/5`**. ## Decisions made in this plan (spec ambiguities, my calls)

1. **Registry.**
   - It is a named instance whose immutable snapshot lives in `:persistent_term`. Resources are keyed `{schema, table}` and the graph spans schemas.
   - `:schemas` is required when the resources span several schemas.
   - The registry answers PGRST002 (503) until it has loaded.
2. **Functions and result scoping.**
   - `PgRest.Function` has `result_scope: :stored_rows | :none`, default `:stored_rows`. A returned row survives only if an in-scope stored row matches on the key **and** on every mapped column (`IS NOT DISTINCT FROM`), column-wise because the scoped source selects only schema columns. Fabricated rows and rows with changed attributes are dropped.
   - The checks are static. A resource is custom-scoped when its module defines `scope/2` (`custom_scope?`). VOLATILE + custom-scoped return without `:none` raises at registry start, and so does a custom-scoped return without a PK/`unique_key:` under `:stored_rows`. `:none` functions are listed in one startup warning.
   - Introspected functions declare options through the registry's `function_opts:` map.
   - A hook-narrowed, PK-less return resource fails closed at request time (42501 + `Logger.error`), because it can't be caught statically.
3. **GET on a volatile function** runs in a READ ONLY transaction, as PostgREST does. A function that writes then fails with 25006, which maps to 405. GET isn't refused upfront.
4. **Off by default:** `aggregates` and `plan_enabled`, mirroring PostgREST's defaults. Compat routers enable both.
5. **Timezone** follows v14 semantics, validated against `pg_timezone_names`: ignored under lenient, PGRST122 under strict. Recordings override.
6. **RLS differential fixture.** It is a second, Supabase-shaped database and PostgREST with `anon`, `authenticated` and `authenticator` roles and new RLS tables. Upstream's `postgrest_test_*` roles and `authors_only` aren't used, because Phase 1's `test` instance runs with anon = postgres.
7. **JWT.**
   - Built in: HS256 via `:crypto`, with no JOSE dependency.
   - Other algorithms need a custom `PgRest.JWT.Verifier`, or `jwt: :context`.
   - `role_claim` is a key path, not JSONPath.
8. **Request GUCs and roles.**
   - `request.path` is relative to the PgRest mount.
   - Repeated request headers are joined with `", "` in `request.headers`.
   - In RLS mode, a login role that is superuser or `BYPASSRLS` raises on first use unless `allow_privileged_login: true`, which downgrades it to a one-time warning (S-H3). `bypasses_rls?` is computed from `session_user`, outside the request transaction.
   - `rls[:roles]` is a required allowlist. A role claim of `none`, `session_user` or anything outside it is rejected before SQL with the same 401 22023 body as a nonexistent role, so the two are indistinguishable.
   - The JWT secret may be `{:system, var}`, an MFA or a function, resolved per request (S-L3).
9. **401 vs 403 outside RLS mode** comes from the `anonymous?` option. Its default is `context[:role] in [nil, :anon, "anon"]`.
10. **Hook.**
    - `authorize_query/5` columns are physical column names.
    - Relationship join columns aren't checked.
    - The hook query's `select`/`preload` are stripped. `limit`/`offset`/`order_by`/`group_by` raise, the same predicate contract as `scope/2`.
    - The hook returns `{:ok, q, columns: …, limit: …}`. `limit:` is a per-parent cap, `LEAST(request limit, hook limit)` inside each lateral. On the root, `count=exact` counts the capped set.
    - The hook builds on Phase 1's fail-closed per-resource `authorize/4`. For each touched resource (root, embeds, junctions, RPC result resources, write targets), `authorize/4` runs first and the hook only narrows. Functions also get `:execute`, and plan output `:explain`.
    - A missing callback denies (no `authorize/4` → `:execute`/`:explain` denied; no `authorize_query/5` → `authorize/4` decides everything). The hook's `aggregates:` and `count:` default to `false`, so a hook that says nothing denies them (S-M1).
    - Writes with filters/representation/count get two hook calls on the target: `:read` (filters, order, `RETURNING`, counts) and the write op (payload, check). Hook columns are intersected with the resource's `readable:`/`writable:` (S-H1).
    - Constraint-violation `details` are scrubbed whenever the effective source or an allowlist is not the identity (S-H5).
11. **PUT** uses the `operation: :create` changeset path. **OPTIONS** runs no query and no authorization, and CORS is left to the host app.
12. **Deferred beyond 0.2** (listed in `phase2_backlog.md`): computed fields and relationships, CSV and form request bodies, raw-body RPC params, OpenAPI root, Proxy-Status, error verbosity. The response GUCs are **in** 0.2 (Task 6b).

    **Deferred / future note:** PostGIS / GeoJSON (`application/geo+json`) and extension-aware types: future, via the planned syntax/extension adapter layer; not in 0.2. `application/geo+json` therefore takes the normal PGRST107 path (one cheap `only: :pgrest` scenario in Task 8).
13. **Response GUCs** are read as two extra columns of the same wrapper statement, mirroring `Statements.hs`, so the one-statement rule holds. A follow-up `SELECT` in the same transaction is the documented fallback if a recording disagrees. GUC headers replace same-named generated headers (case-insensitive), and repeated GUC headers are all sent. Scenarios assert custom headers through the per-scenario `headers:` allowlist extension.
14. **PUT ownership.** PUT reuses Phase 1 Task 13's guarded `ON CONFLICT … DO UPDATE … WHERE EXISTS (SELECT 1 FROM (<ScopedSource>) s WHERE (s.<pk>) = (<table>.<pk>))`, the correlated form (P-H4). Zero returned rows means 42501 and rollback, and the post-write check still runs. PUT always needs `:read`, because it always has PK filters. The SET list comes from the supplied-key mask, and inserted vs updated from `pgrst.inserted`.
15. **Ports and variants** (only rows of the Phase 1 port table).
    - pg-safeupdate gets no PostgREST, because there is no port for one. It is verified at the SQL level on `db_safeupdate` (54325), and the HTTP expectations are copied from upstream `PgSafeUpdateSpec.hs`.
    - The JS e2e PgRest server uses `54328`.
16. **Catalog.** Phase 2 extends Phase 1's `PgRest.Catalog` with `facts/1` (`%PgRest.Catalog.Facts{}`, cached under `{PgRest.Catalog, repo, :facts}`). It doesn't turn the module into a struct, and `column_defaults/3` is untouched.
17. **CSV coverage** reads committed `test.csv_edge_cases` rows rather than rolled-back inserts. Bodies are compared by `Compare.diff`'s raw-text mode and also byte-for-byte.
18. **Fixture readiness and state.** Every Phase 2 database uses the Phase 1 reload-marker protocol (`public.pgrst_reload_<unix_ms>`, granted to the instance's anon role) and `DROP DATABASE … WITH (FORCE)`. Each has its own sequence baseline for `reset_sequences!/1`. The Node suite runs with `--test-concurrency=1` under the reset protocol, in both engine orders.
19. **RPC introspection exposure (S-C1).**
    - `introspect:` takes `mode: :app | :rls`. In `:app` mode it requires `only:`/`except:` or an `authorization:` module exporting `authorize/4`, or registry start raises. The Plug cross-checks the registry's recorded mode and module on its first request.
    - In `:rls` mode `as_role:` defaults to the `rls[:roles]` allowlist (which contains `default_role`), not to `default_role` alone. The resolutions name `default_role`, but that would hide `authenticated`-only functions and break PostgREST parity (`privileged_hello` → PGRST202 instead of 200). Postgres still enforces `EXECUTE` per call.
    - Extension-owned functions and `trigger`/`event_trigger`/`internal` returns are always skipped.
20. **Plan gating (S-M4).** A plan that is disabled, refused by `plan_enabled`'s function, denied `:explain`, or an `analyze` write without `tx_end: :commit_allow_override` + `tx=rollback` all answer the same 406 PGRST107, so a client can't learn that plans exist.
21. **Setup statement (P-M2).** Read-only, `statement_timeout`, timezone and RLS GUCs are pairs of one `set_config` `SELECT`; no `SET TRANSACTION`. The repo `timeout:` is `statement_timeout` + 1 s so Postgres cancels first.
22. **RPC POST bodies** use Phase 1's `PgRest.BodyReader` raw bytes when present, else `conn.body_params` re-encoded once; on the latter path PGRST202 key order follows the decoded map.
23. **Deferred / future:** PostGIS / GeoJSON (`application/geo+json`) and extension-aware types: future, via the planned syntax/extension adapter layer; not in 0.2.
