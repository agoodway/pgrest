# PgRest 0.2 — Phase 3: Hardening, Performance & Release — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Harden the Phase 1–2 compatibility claim (randomized differential testing against PostgREST, an 85 % line-coverage gate, the remaining SHOULD-PORT scenarios), then prove, with committed numbers and scripts, that PgRest matches PostgREST v14 on the same database (same plan shape, same statement count, p95 within 1.25×), make every pipeline stage observable through telemetry, fix the gaps the comparison finds, and ship 0.2.0 with the demo app upgraded.

**Architecture:** Hardening first (Tasks 1–3): a StreamData generator over the compat fixture schema sends each generated request to both engines through the Phase 1 runners and `PgRest.Compat.Compare.diff/3`; shrunk failures become committed scenario files; `excoveralls` gates `lib/` coverage in CI; the SQL/JS SHOULD-PORT backlog is closed or recorded as out of scope. Telemetry and performance next (Tasks 4–13), docs, demo and release last (Tasks 14–16). A `:bench` Mix env compiles `bench/lib` alongside `lib` and `test/support` (so the Phase 1 compat resources and `PgRest.Compat.Compare` are reused). A `bench` docker-compose profile adds a second PostgREST (`postgrest_bench`), a containerized PgRest server (`pgrest_bench`, Bandit behind `Plug.Parsers` with `PgRest.BodyReader`), an `ab` container (peak throughput only) and an `oha` container (open-loop latency), all on the compose network against one scaled database `pgrest_bench` (Phase 1 fixture DDL, generated rows, schema `test`). A bench-only override file `bench/compose.bench.yml` pins CPUs and loads `auto_explain` on `db`. The bench server mounts four routes: `/rls` (RLS mode), `/scope` (`scope/2` predicates mirroring the bench RLS policies, including one joined scope), `/changeset` (a `tasks` resource with a custom changeset) and `/` (default mode). **Targets apply to `/rls` and `/scope` against PostgREST with the same JWT**; `/` is reported separately as "PgRest default mode". `mix pgrest.bench` seeds, checks response parity, captures both servers' plans (via `Accept: application/vnd.pgrst.plan+json`, and for the plan target the plan `auto_explain` logs on the ≥ 6th execution on one backend), diffs normalized plans, measures `pg_stat_statements` deltas, runs `ab` peak and `oha` open-loop load and Benchee micro-benchmarks, checks targets and writes `bench/REPORT.md` + JSON results.

**Tech Stack:** Elixir 1.19 / OTP 28, Ecto SQL 3.14, Postgrex 0.22, `:telemetry` 1.4, Bandit 1.14, Req 0.5, StreamData `~> 1.1` (Phase 1 test dep), ExCoveralls `~> 0.18.5` (new, `only: :test`), Benchee `~> 1.5` (new, `only: [:test, :bench]`), ApacheBench 2.3 (`ab`, from the `httpd:2.4-alpine` image; peak throughput only), `oha` 1.16.0 (image `ghcr.io/hatoo/oha:1.16.0`, released 2026-08-23; open-loop latency; **pulled as an image, never installed on the host**), Postgres 16 `auto_explain` (contrib, ships in `postgres:16`), Postgres 16 + `pg_stat_statements`, PostgREST v14 (same pinned tag as Phase 1), GitHub Actions.

## Global Constraints

- **Drop-in parity governs:** a supabase-js app must just work; **the recorded PostgREST response is authoritative**. Benchmarks only compare servers after their responses for the scenario are equal (Task 6). Randomized cases (Task 1) never relax `Compare.diff/3`; a diff is a bug in PgRest or in the generator, never an allowlist entry.
- Comparison target: the exact `postgrest/postgrest:v14.x` tag pinned in Phase 1's `docker-compose.yml` — the bench service reuses that tag, never `latest`.
- **Targets (spec, verbatim values):** PgRest p95 ≤ **1.25×** PostgREST per scenario; **identical statement count** per scenario; **plan shape equivalent (same scan/join strategy) for all read scenarios**; expect **1 statement per read** for PgRest (plus RLS GUC setup when enabled). Results committed under `bench/` with the scripts that produce them.
- **Where the targets apply (P-H2):** every read scenario and both write scenarios (plus `upsert-scoped`) run on PgRest `/rls` **and** `/scope` against PostgREST with the same JWT. The targets are evaluated there, and `--check` fails only on them. `/` runs the same scenarios against PostgREST as `bench_service` and is reported separately as **"PgRest default mode"**. It is not a target, because it does less work than PostgREST (no transaction, no role switch). The `/changeset` scenario is reported on its own. One documented exception *(my call)*: a scoped write's post-write check is one extra statement by design (Phase 1; upgrade guide). `Statements.check/3` records it as `:known_gap`, listed under "Known differences" in the report. It is never silently passed.
- **The plan target uses warm plans (P-H1):** a cached named statement may switch to a generic plan after 5 custom executions. So the plan target compares the plan each server actually ran on its ≥ 6th execution of the scenario on one backend connection (Task 7, via `auto_explain`). One-off `EXPLAIN` plans are kept for buffers and row estimates.
- Dataset: deterministic (same seed ⇒ byte-identical data), scales `small` (100k tasks) and `large` (1M tasks). *(Scale table: my call, Task 5.)*
- Perf CI runs **nightly and on demand only** (`schedule` + `workflow_dispatch`); the differential suite stays on every PR. Phase 1's `ci.yml` keeps its jobs; Task 1 adds the N=500 randomized step to its `differential` job and Task 2 swaps its `test` job's `mix test` for the coverage run. The N=5 000 randomized run is nightly (`nightly.yml`, Task 1).
- **Load methodology (P-M4):**
  - `ab` (`httpd:2.4-alpine` image) measures **peak throughput only**.
  - The latency verdict comes from an **open-loop** run with `oha` (`ghcr.io/hatoo/oha:1.16.0`, `-q <rate> --latency-correction`). It runs at **50 % of the slower server's peak rate**, for **≥ 20 s** per run, with **5 repetitions alternating servers**. A p95 coefficient of variation > 15 % across the 5 is `inconclusive`.
  - Write scenarios run **last**, with `VACUUM (ANALYZE)` of the written table between repetitions.
  - CPUs are pinned with `cpuset`: `db` apart from the servers, and the load generators apart from both. The PgRest container runs with `ERL_FLAGS="+sbwt none +sbwtdcpu none +sbwtdio none"`. The report records the cpusets, flags, rate and image tags.
  - **Never install a browser or a load tool on the host.** Pulling the pinned `httpd:2.4-alpine` and `ghcr.io/hatoo/oha:1.16.0` images is fine. (oha 1.17.0 was released on the plan date, too new to pin.)
- **Bench routers:**
  - Every bench route sets `tx_end: :commit_allow_override`. The bench PostgREST runs `PGRST_DB_TX_END=commit-allow-override`, and every bench write and `options=analyze` capture relies on `Prefer: tx=rollback`.
  - Every route keeps the default `statement_cache` and sets `max_limit: 1000` (= `PGRST_DB_MAX_ROWS`; both now clamp every embed level).
  - `/rls` passes `roles: ["authenticated", "bench_service"]`.
  - The bench server runs `Plug.Parsers` with `body_reader: {PgRest.BodyReader, :read_body, []}` in front of every route, as a Phoenix host would (P-M1).
- Telemetry: reuse Phase 1 events exactly — `[:pgrest, :request]` span (`%{resource, method, status}`) and `[:pgrest, :query]` span (`%{sql, params_count, rows}`), one `:query` span per SQL statement. New metadata keys are additive. **Never put bind-parameter values in telemetry metadata, logs or bench output.** That covers three more places:
  - The host repo's own query event and Ecto's `:debug` log. Every PgRest repo call passes `log: false` and `telemetry_options: [pgrest: true]` (Phase 1; S-M3).
  - EXPLAIN text. `telemetry_plan: :plan` uses `EXPLAIN (GENERIC_PLAN, FORMAT JSON)`, which prints `$n`; `:analyze` is documented as emitting values (S-M4).
  - There is no hard dependency on OpenTelemetry.
- Ecto schemas registered as resources remain the contract; one SQL statement per read; no per-row or per-embed queries.
- `mix quality` must pass at the end of every task (compile --warnings-as-errors, format, sobelow, ex_dna, doctor, credo --strict, dialyzer). Bench code is compiled in `:test` too, so quality covers it.
- **Git:** never run `git commit`, `git push`, `git tag`, `git add` or anything that changes the index or HEAD, and never `mix hex.publish`. The maintainer stages and commits. A "Suggest a commit message" step means: leave the work in the working tree and propose a message (no AI attribution); the maintainer decides if and when to commit.
- **Every implementer and reviewer agent loads the `elixir-genius` skill (Skill tool) before writing or reviewing code**, plus `elixir-phoenix-guide:elixir-essentials`; `elixir-phoenix-guide:ecto-essentials` for Ecto/SQL work; `elixir-phoenix-guide:testing-essentials` for tests; `elixir-phoenix-guide:telemetry-essentials` for Task 4 and any handler/Logger code; `elixir-phoenix-guide:otp-essentials` for the bench server supervision tree.
- **Subagent models:** implementers `sonnet`; spec/code reviewers and final branch review `opus`; mechanical search/replace `haiku`. Never `fable` (reserved for the separate security/performance audit of the plans).
- Idiomatic Elixir: `with` over nested `case`; function-head matching over conditionals; predicates end in `?`; module-level `alias`/`import` only; no process dictionary; `Req` for HTTP; `Jason` for JSON; structured `Logger` calls (`Logger.info("msg", key: v)`), never interpolated.
- **Never create atoms from request input** (unchanged from Phase 1). Bench scenario ids are strings.
- Ports: **the single port table lives in Phase 1's Global Constraints**; every port used here comes from it. Phase 3 uses only `54330` (`postgrest_bench`), `54331` (its admin), `54332` (`pgrest_bench`); `54333` is used only by the hand-started PostgREST in Task 15 Step 5 (local check, not in compose). **Compose is a test harness only (S-M5):** every bench port binds `127.0.0.1:<port>:<container port>`, and no bench service has a `restart:` policy. The bench services sit under the compose file's "test harness only" header. `bench/README.md` is headed "test harness only" and never prints the `authenticator` password, the shared JWT secret or a superuser anon role. Overrides: `PGREST_DB_PORT`, `PGREST_BENCH_POSTGREST_URL` (default `http://localhost:54330`), `PGREST_BENCH_PGREST_URL` (default `http://localhost:54332`).
- Randomized differential testing (Task 1): fixed seed `PGREST_PROP_SEED` (default `20261114`), `max_runs` from `PGREST_PROP_RUNS` — **500 in the PR `differential` job, 5 000 nightly**. Read-only requests run async; mutations run only under Phase 1's stateful protocol (`async: false`, `reset_sequences!/1` before each engine, `Prefer: tx=rollback`).
- Coverage (Task 2): `mix coveralls` in CI fails below **85 %** line coverage of `lib/` (maintainer's call). `test/support`, `bench/` and `demo/` are not measured.
- Version goes `0.1.0` → `0.2.0` only in Task 16.
- GitHub Actions in the workflows this plan creates or edits (`nightly.yml`, `bench.yml`, the `ci.yml` steps) are **pinned by full commit SHA**, with a `# vX.Y.Z` comment (Phase 1, S-L6).
- **PostGIS and GeoJSON are descoped from 0.2** and are future work only. This phase has no scenarios, benchmarks, release checks or doc claims for them. README may name them only under "Not yet supported".

## Review Focus

1. **Bind-parameter values leaking** into telemetry metadata, the default logger, **the host repo's query event, Ecto's `:debug` log**, **`telemetry_plan` EXPLAIN text** (a custom plan prints `Index Cond: (x = 'value')`), `auto_explain` captures or `bench/results` (filter values can be PII). Expected:
   - Only SQL text with `$n` placeholders and `params_count`.
   - Every repo query event PgRest causes is tagged `options: [pgrest: true]`, and no Ecto log line appears for it.
   - `telemetry_plan: :plan` plans contain `$1`, never the value.
   - `auto_explain` runs with `log_parameter_max_length = 0`.
   Tests owned by Task 4 (`no params in any event`, extended to the repo event and a `:debug` log capture), Task 7 (warm capture settings) and Task 11 (report scan).
2. **Benchmarking different work:** any of these makes the comparison meaningless:
   - a server silently truncating (`max_limit` ≠ `db-max-rows`, or one side not clamping embeds);
   - a 4xx counted as a fast request;
   - an unordered to-many level;
   - RLS policies or `/scope` predicates that filter nothing;
   - a write that commits (missing `Prefer: tx=rollback`, or `tx_end` not set to `:commit_allow_override` on a bench route);
   - **target verdicts drawn from `/` (superuser, no transaction) instead of `/rls` / `/scope`**;
   - a write body that bypasses `Plug.Parsers`.
   Expected: the run aborts for that scenario, naming it. Tests owned by Task 5 (RLS and scope precondition: two JWT users see different counts, and `/scope` agrees with `/rls`; router options test), Task 6 (parity gate, to-many order check, table checksum around writes), Task 9 (non-2xx ⇒ invalid run) and Task 11 (targets evaluated only on `:rls`/`:scope`).
3. **False or unreproducible randomized failures:** a generated request whose response order is unspecified (no `order`, or an embed without `rel.order`), a sequence advanced by the other engine's rolled-back insert, or a failure that cannot be replayed from its seed. Expected: generated reads always order every level, mutations follow the baseline protocol, and every failure prints its seed and is saved as a scenario file that fails the same way. Test owned by Task 1.
4. **`pg_stat_statements` contamination:** the reset call, the snapshot query, Postgrex type bootstrap on fresh connections, PostgREST schema-cache queries, other databases. Expected: only the measured server's per-request statements are counted. Test owned by Task 8.
5. **Noisy or asymmetric measurements** turning into a false pass or fail. Causes to watch: Docker Desktop port-forwarding on macOS, closed-loop saturation, CPU contention with the database, BEAM scheduler busy-wait under a CFS quota, dead tuples from rolled-back writes, and run-order drift. Expected:
   - Both servers and the load generators run in containers on the same network, with equal CPU limits and pinned cpusets (`db` apart).
   - The latency verdict comes from open-loop `oha` at 50 % of the slower peak, ≥ 20 s, 5 alternating repetitions.
   - Writes run last, with `VACUUM` between repetitions.
   - PgRest runs with `+sbwt none +sbwtdcpu none +sbwtdio none`.
   - A p95 CV > 15 % across the 5 is `inconclusive`, not pass or fail.
   Tests owned by Task 5 (compose config test) and Task 9.
6. **Plans that production never runs:** a one-off `EXPLAIN` shows the custom plan, while a promoted named statement may run a generic plan from its 6th execution on. Expected: the plan target uses the `auto_explain` plan of a ≥ 6th execution on one backend PID. The custom-vs-generic difference is reported as `:info` `:generic_plan_switch`. Statement-count measurements happen after warm-up beyond `statement_cache.promote_after`. Tests owned by Task 7 and Task 8.
7. **Statement classes:** a `SET TRANSACTION` counted as `:main` would break `main == 1`. Expected: `classify/1` puts it in `:setup`. In RLS mode PgRest sends one folded `set_config` setup statement (Phase 2), so `pgrest.setup <= postgrest.setup` holds. Test owned by Task 8.

### Task 1: Randomized differential testing (StreamData)

**Files:**
- Create: `test/support/compat/gen.ex` (`PgRest.Compat.Gen`), `test/support/compat/gen/save.ex` (`PgRest.Compat.Gen.Save`), `test/compat/random_differential_test.exs` (reads, `async: true`), `test/compat/random_differential_stateful_test.exs` (mutations, `async: false`), `test/compat/scenarios/random/.gitkeep`, `.github/workflows/nightly.yml`
- Modify: `test/support/compat/scenario.ex` (`Scenario.load/1` also accepts a directory area: `"random"` loads every `test/compat/scenarios/random/*.exs`), `.github/workflows/ci.yml` (job `differential` adds `PGREST_PROP_RUNS=500 mix test --only random_differential --seed 20261114`), `test/test_helper.exs` (exclude `:random_differential` by default)
- Test: `test/compat/gen_test.exs`, plus the two property modules above

**Interfaces:**
- Consumes: `PgRest.Compat.Resources.all/0`, each resource's `__pgrest_config__/0` (`field_sources`, `types`, primary key), `PgRest.SchemaGraph.build/1` and `%PgRest.SchemaGraph.Relationship{kind:}` (to-one = `:m2o | :o2o`), `PgRest.Compat.Scenario.run_pgrest/1` / `run_postgrest/1`, `PgRest.Compat.Compare.diff/3`, `PgRest.Compat.Fixture.sequence_baseline/0` and `PgRest.Compat.Fixture.reset_sequences!/1`, `PgRest.Compat.Fixture.load!/0` (all Phase 1).
- Produces:
  - `PgRest.Compat.Gen.read() :: StreamData.t(scenario)` and `PgRest.Compat.Gen.mutation() :: StreamData.t(scenario)`. A `scenario` is the Phase 1 scenario map (`id`, `method`, `path`, `headers`, `body`, `sort: false`, `plug_opts: []`, `only: :both`, plus `stateful: true` for mutations). `id` is `"random/" <> first 12 hex chars of sha256(method <> path <> inspect(headers) <> inspect(body))`.
  - Component generators (each `StreamData.t/1`, all public so `gen_test.exs` can sample them): `filter(resource)`, `logic(resource, depth \\ 2)`, `select(resource, depth \\ 2)`, `order(resource)`, `page()`, `prefer(kind :: :read | :mutation)`.
    - `filter/1` — a column of the resource and an operator from exactly this list: `eq neq gt gte lt lte like ilike match imatch in is isdistinct cs cd ov sl sr nxr nxl adj fts plfts phfts wfts`, plus the `not.` prefix and the `any`/`all` modifiers on `eq neq gt gte lt lte like ilike match imatch`. The operator must suit the column type (`types` from the config: ranges for `sl…adj`, arrays/jsonb/ranges for `cs cd ov`, text/tsvector for the fts family, any type for `eq`/`in`/`is`). Values: typed literals, unicode text with `,.:()"\` and spaces, `in` lists quoted with `"` and backslash-escaped, `*` wildcards for like. About 1 in 10 values is deliberately malformed for the column type (e.g. `id=eq.abc`), so error responses (`22P02` and friends) are compared too.
    - `logic/2` — `or=(…)` / `and=(…)` / `not.or=(…)` trees nesting to `depth`, leaves from `filter/1`, plus embedded logic `rel.or=(…)` on a selected embed.

The schema also adds two functions, both read-only (STABLE, no writes): `search_tasks(q text) returns setof tasks` and `project_stats(project_id int) returns table(...)`. The demo has no VOLATILE function.

**Nothing persists on the deployed demo.** Add PostgREST's `db-tx-end` modes `:rollback` and `:rollback_allow_override` to the `tx_end` Plug option, as generic parity, not demo code.
- `:rollback` ends every request's transaction with ROLLBACK and ignores `Prefer: tx=`.
- `:rollback_allow_override` rolls back by default and honours `Prefer: tx=commit`.
- `Preference-Applied` follows upstream for each mode.
- These go in `lib/pg_rest/plug.ex` and the executor's transaction end, with recorded scenarios against a PostgREST started with `PGRST_DB_TX_END=rollback`, using the Phase 1 limits-style service pattern.

The demo endpoint sets `tx_end: Application.get_env(:demo, :tx_end, :commit)`, and `config/runtime.exs` sets `:rollback` in prod. Write showcase entries (insert, upsert, dry-run update) therefore return real responses on Fly and leave no rows. Demo test: a POST in the `:rollback` config returns 201 with the row, and a follow-up GET doesn't find it.
